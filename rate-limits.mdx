Each user gets 100 requests per minute across every key and every authenticated endpoint. Use this page to size a polling loop and to handle a `429` response.

## Know the budgets

- The request budget is 100 requests per minute per user in a sliding window. All keys on the account share it.
- The batch routes (`POST /api/v1/traders/batch` and `POST /api/v1/markets/intel/batch`) also reserve one item unit per requested item from a budget of 2500 item units per minute. Duplicate and invalid items count.
- 2500 is 100 requests times 25 items. A full minute of 25-item batches fits inside the item budget, so the request budget is the effective ceiling.
- The item budget can still deny at a window boundary. Honor a `429` from either budget.
- `GET /api/v1/usage` does not spend the request budget. It has its own guard of 100 reads per minute per user.
- `GET /api/v1/health` is public and limited to 120 requests per minute per IP.
- `GET /api/v1/stream` caps concurrent connections per key. A connection over the cap returns `429` with `Retry-After`.

## Read the headers

Every authenticated response carries the standard and the legacy spelling:

```
RateLimit-Limit:       100
RateLimit-Remaining:   84
RateLimit-Reset:       42
X-RateLimit-Limit:     100
X-RateLimit-Remaining: 84
X-RateLimit-Reset:     1710772860
X-Request-Id:          req_550e8400
```

| Header | Meaning |
|---|---|
| `RateLimit-Limit` | Requests allowed per window. |
| `RateLimit-Remaining` | Requests left in the current window. |
| `RateLimit-Reset` | Seconds until the window resets. |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the window resets. |
| `X-Request-Id` | Request identifier. Include it in a support request. |

Batch responses add four headers:

| Header | Meaning |
|---|---|
| `X-Request-Cost` | Item units this call charged. |
| `X-Batch-RateLimit-Limit` | Item units allowed per minute. |
| `X-Batch-RateLimit-Remaining` | Item units left in the current window. |
| `X-Batch-RateLimit-Reset` | Unix timestamp when the item window resets. |

Browser JavaScript can read every header above on `/api/v1/*` responses.

## Handle a 429

An over-budget request returns `429` before any work runs:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 12
```

```json
{
  "object": "error",
  "error": {
    "code": "rate_limited",
    "message": "Rate limit exceeded. Retry after 12s.",
    "doc_url": "https://docs.0xinsider.com/api-reference/introduction#rate-limits",
    "param": null,
    "retry_at": "2026-08-29T12:00:12Z"
  },
  "meta": { "request_id": "req_example", "cached": false, "cost": 1 }
}
```

1. Read `Retry-After` in seconds. `error.retry_at` names the same instant as RFC3339.
2. Wait that many seconds.
3. Retry once. Cap the retry count.

Read `Retry-After` on every retryable error, not only on `429`. See [Errors](/errors#honor-retry-after).

<CodeGroup>
```javascript JavaScript
async function fetchWithBackoff(url, opts = {}, maxRetries = 5) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const res = await fetch(url, opts);
    if (res.status !== 429) return res;

    const wait = Number(res.headers.get("retry-after") ?? 1) * 1000;
    await new Promise(r => setTimeout(r, wait));
  }
  throw new Error("Rate limit retries exhausted");
}

const res = await fetchWithBackoff(
  "https://api.0xinsider.com/api/v1/whale-trades?limit=50",
  { headers: { Authorization: `Bearer ${process.env.OXINSIDER_API_KEY}` } }
);
const body = await res.json();
```

```python Python
import os, time, requests

def get_with_backoff(url, params=None, max_retries=5):
    headers = {"Authorization": f"Bearer {os.environ['OXINSIDER_API_KEY']}"}
    for _ in range(max_retries):
        r = requests.get(url, params=params, headers=headers)
        if r.status_code != 429:
            return r
        time.sleep(int(r.headers.get("Retry-After", "1")))
    raise RuntimeError("Rate limit retries exhausted")

body = get_with_backoff(
    "https://api.0xinsider.com/api/v1/whale-trades",
    params={"limit": 50},
).json()
```
</CodeGroup>

## Stay under the budget

- Cache responses. Do not poll every second.
- Paginate with `cursor`. Do not re-read the first page.
- Use a larger `limit`. One request with `limit=100` costs one request.
- Batch known IDs. One batch call costs one request and one item unit per item.
- Watch `RateLimit-Remaining`. Pause when it is low.
- Run one poller per account. Do not let each process poll on its own.
- Use conditional GETs on read endpoints.

## Use conditional GETs

Deterministic read endpoints return an `ETag`. Send it as `If-None-Match` to get `304 Not Modified` with an empty body when the payload did not change.

Endpoints with a `304` response:

- Trader, trader context (JSON), trader P&L, and position timeline.
- Positions, large positions, whale trades, whale trade by ID, and whale trades history.
- Leaderboard, trending wallets, Pick of the Day, and its archive.
- Explore markets, smart-money flows, sharp-money flows, sports-edge signals, and sports-edge observations.
- Market intel, market snapshot, and market candles.
- Insider radar, single radar flags, and health.

Report snapshots return no `ETag`. Check each endpoint's response table for `304`.
